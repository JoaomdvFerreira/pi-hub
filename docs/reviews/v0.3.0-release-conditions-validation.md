# Pi-Hub v0.3.0 Release Conditions Validation

Date: 2026-08-10
Approved validation document: `v0.3.0-release-conditions-validation.md` (version 0.1)
Validation branch: `release/v0.3.0-readiness`

## Executive summary

- **Final readiness classification: NOT READY**
- **Release risk: 70/100 (Orange)**
- Condition counts: 3 PASS, 1 FAIL, 5 BLOCKED, 0 NOT EXECUTED.
- **Release recommendation: DO NOT RELEASE.** RC-04 is a current packaging/signing
  blocker. The other blocked conditions must be completed as described below; RC-09
  additionally requires explicit operator authorization and is not a product failure.

## Baseline and scope

The release candidate started from `main` commit
`ceb4e0bc257517e5eb10c4bcc1f2e096d4398f87` (`Merge pull request #10 from
JoaomdvFerreira/fix/prrr-001-historical-trends-loop`). `origin/main` was fetched
and local `main` fast-forwarded from `11201cf` before this branch was created.

The required PRRR-001 remediation commit
`0cf931ecc66d6494456cb1e7bfa727f5180c10ca` is an ancestor of the candidate.
Versions were synchronized from `0.2.0` to `0.3.0` in `package.json`,
`src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json`; normal Cargo tooling also
updated only the root `pi-hub` entry in `src-tauri/Cargo.lock`.

The validation environment could build locally, but could not safely replace a
primary installation, provide a staging/published updater feed, or provide a
reachable non-critical device. No live device operation was performed. RC-09 was
not authorized and was not attempted. No tag, GitHub Release, upload, merge, or
AIQT-state change was performed.

## Residual risks and exact operator actions

1. Resolve the local Tauri release-build timeout in a controlled Windows release
   environment, then rerun the established signed build. Verify the generated
   `0.3.0` MSI/NSIS artifacts, updater archive, and corresponding `.sig` files;
   do not publish them yet.
2. On a disposable Windows VM or test machine, clean-install the signed candidate,
   launch it, and confirm the visible version is `0.3.0` without a first-launch
   failure.
3. Host a signed candidate updater archive and candidate `latest.json` at a
   non-production/staging endpoint, then update a disposable `v0.2.0` installation
   and confirm signature verification, update completion, and successful `0.3.0`
   launch. Do not alter the published `v0.2.0` release.
4. Against a reachable non-critical supported device, perform RC-07 read-only M11
   visibility checks and RC-08 elapsed M12 accumulation checks for device, service,
   and container trends.
5. If desired, explicitly authorize one minimal representative M10 controlled
   administration action on a non-critical device (not shutdown unless separately
   authorized with an independent power-restoration path), then validate its
   confirmation, `sudo -n`, bounded verification, recovery, Activity, and planned-
   offline/alert-suppression behavior.

## Final decision

**DO NOT RELEASE**

RC-04 fails because the generated `0.3.0` installers are not accompanied by the
required updater signatures/artifacts and the signed build did not complete. The
remaining blocked validation must be completed before release; RC-09 remains
blocked awaiting explicit operator authorization.
